# How tools turn on the Teams web tree

Status: on 2026-11-09 the user decided that Mysli may write `AXEnhancedUserInterface` on the Teams app. `TeamsWebContentSwitch` does this with the limits in "Consequence for Mysli", item 3. It turns the flag off again at Pause and Stop. It does not retry when the tree stays empty. Nobody has checked the write in a real call yet.

Checked on 2026-11-09 with `gh api`, GitHub search, Microsoft Learn, and Microsoft support pages. These are observations of source code and documents. No third-party code was installed, built, or run. Nothing ran against Teams. This note builds on the [earlier open-source note](2026-10-29-teams-open-source.md) and does not repeat it.

Each finding has one of four labels:

- **Source.** We read it in code at the pinned commit.
- **Documented.** An official page says it.
- **Reported.** Another project measured it or wrote it. We did not check it.
- **Unconfirmed.** It is our own inference.

## Our measurement on 2026-11-09

- Teams is `com.microsoft.teams2` version 26289.204.5281.6363, updated on 2026-11-06. The host app is `MSTeams`. A second process, "Microsoft Teams WebView", is Edge WebView2 for Mac with Edge framework 156.0.4314.42. Its flags include `--embedded-browser-webview=1` and `--enable-features=msWebView2EnableMinimalWindow,...`.
- Each Teams window has 12 AX nodes. They are the shell groups `RootView`, `NonClientView`, `EmbeddedBrowserTabRootView` (size 0×0), `NativeFrameViewMac`, `ClientView`, and `EmbeddedBrowserDownloadView` (size 0×0), plus three title-bar buttons. There is no `AXScrollArea` and no `AXWebArea`.
- `AXManualAccessibility = true` returns -25205 (`kAXErrorAttributeUnsupported`) on the `MSTeams` pid and on the WebView pid. Nothing changes after the write.
- None of the 8 "Microsoft Teams WebView" processes has `--disable-renderer-accessibility`, `--disable-platform-accessibility-integration`, or `--force-renderer-accessibility` in its command line. So no start flag blocks the tree.
- On 2026-11-04, an older Teams showed `AXScrollArea > AXWebArea` with the call controls.

## Main findings

1. **Reported.** The working switch is `AXEnhancedUserInterface = true` on the application element of the `MSTeams` process. Two projects tried the two attributes one at a time on Teams, and only this one worked. Two more projects write both attributes and see the tree. One project that writes only `AXManualAccessibility` saw the tree, but on a Mac where other tools that write `AXEnhancedUserInterface` were installed.
2. **Source.** `AXManualAccessibility` is an Electron attribute. Chromium does not handle it. Teams uses Edge WebView2, not Electron, so -25205 is the expected answer.
3. **Reported.** After the switch is on, the web tree stays on until Teams quits, even if a client sets the switch back to false. Three projects say this.
4. **Unconfirmed.** The 2026-11-06 update restarted Teams. Something turned the tree on in the earlier Teams process, and the restart turned it off. This is the most likely reason for the difference between 2026-11-04 and 2026-11-09.
5. **Reported.** Reads alone did not turn the tree on in a measured case. The write is not always enough at once either. Two projects saw an empty tree for minutes after the write.
6. **Documented.** Microsoft publishes no documentation for WebView2 on Mac, so there is no documented setting or variable for Teams accessibility on Mac.

## What the 12 nodes are

- **Reported.** A captured tree of an awake Teams 26276 window in [ai-translator](https://github.com/dotienphong/ai-translator/blob/002e12273f56f9818ab0ccbe9a149585716a1148/scripts/speaker-recipes/fixtures/teams-macos-named-meeting.jsonl) has the same shell: `RootView > NonClientView > (EmbeddedBrowserTabRootView, NativeFrameViewMac > ClientView)`. In that tree, `ClientView` holds `AXScrollArea > AXWebArea`.
- **Unconfirmed.** Our tree is the normal shape of a Teams window whose web tree is off. It is not a new layout. `EmbeddedBrowserTabRootView` is in the awake tree too.
- **Source.** `RootView`, `NonClientView`, `ClientView`, and `NativeFrameViewMac` are class names of Chromium's views toolkit, for example [native_frame_view_mac.h](https://github.com/chromium/chromium/blob/371d3a70e4d0e076059ab773733d8ee5263e0d21/ui/views/window/native_frame_view_mac.h#L18). Chromium can show a tree from one process inside a window of another process. It sends tokens of the private AppKit class `NSAccessibilityRemoteUIElement` ([native_widget_ns_window_bridge.mm](https://github.com/chromium/chromium/blob/371d3a70e4d0e076059ab773733d8ee5263e0d21/components/remote_cocoa/app_shim/native_widget_ns_window_bridge.mm#L764-L767), [remote_accessibility_api.h](https://github.com/chromium/chromium/blob/371d3a70e4d0e076059ab773733d8ee5263e0d21/ui/base/cocoa/remote_accessibility_api.h)).
- **Unconfirmed.** The "Microsoft Teams WebView" process probably serves this tree into the `MSTeams` window in the same way.

### Why `AXManualAccessibility` returns -25205

**Source.** Electron adds `AXManualAccessibility` to `accessibilityAttributeNames` and to `accessibilityIsAttributeSettable`. For this attribute, Electron does not call the AppKit superclass. Its comment says that the superclass call "will log an AXError and make it appear as though the attribute failed to take effect". A GitHub code search of `chromium/chromium` finds no `AXManualAccessibility`. The same search finds `AXEnhancedUserInterface` only in the Chrome application object, the web-app shim, one test, and one header. So every application object that is not Electron answers -25205.

**Reported.** The [ai-translator measurement](https://github.com/dotienphong/ai-translator/blob/002e12273f56f9818ab0ccbe9a149585716a1148/bench/2026-10-26-nguoi-noi/results/teams-chrome.md#L144-L151) and a [Stenly comment](https://github.com/wbunting/stenly/blob/3dcf8921b88741276eb244fb827084d673340fa7/crates/stenly-platform/src/macos/ax_tree.rs#L156-L169) give the same -25205 from Chrome 156. The Teams host and the WebView process also answer -25205, so they behave like Chromium.

### Why `AXEnhancedUserInterface` returns an error that does not mean failure

**Source.** Chromium handles the attribute and then calls `[super accessibilitySetValue:forAttribute:]`.

**Reported.** Projects measured -25208 (`kAXErrorNotImplemented`) while the switch took effect. They saw this in Teams, in Chrome 156, and in Helium with Chromium 151 ([Clavier](https://github.com/fabiogaliano/clavier/blob/d95e6118f990ee6c5e2f1f008f7caa885f38c4ae/clavier/Services/ChromiumAccessibilityWaker.swift)). Do not use the return code as a result. Check the tree for `AXWebArea` or DOM identifiers instead.

## Microsoft documentation

- **Documented.** WebView2 for Mac has no public documentation. A Microsoft contributor wrote in 2024 that Microsoft decided "to discontinue plans for a public release of WebView2 on MacOS and Linux" ([WebView2Feedback #1314](https://github.com/MicrosoftEdge/WebView2Feedback/issues/1314#issuecomment-2211683486)). In 2025 a Microsoft contributor wrote that "webview2 mac is still not available in public stable channels" ([#5384](https://github.com/MicrosoftEdge/WebView2Feedback/issues/5384)).
- **Reported.** The open request [#4503 "Mac Accessibility Support"](https://github.com/MicrosoftEdge/WebView2Feedback/issues/4503), from 2024-04-25, says that Teams on WebView2 works with VoiceOver but not with third-party accessibility apps. It asks for something like Electron's switch. Microsoft only asked a question there.
- **Documented.** On Windows, `WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS` adds arguments to the browser arguments of the app ([Win32 reference](https://learn.microsoft.com/en-us/microsoft-edge/webview2/reference/win32/webview2-idl#createcorewebview2environmentwithoptions)). That page says nothing about Mac. It is unconfirmed whether the Mac build reads this variable.
- **Unconfirmed.** We found no documentation for `msWebView2EnableMinimalWindow`. The name is in [community lists of Edge feature strings](https://github.com/SpyNetGirl/MSEdgeFeatures/tree/d72a21737c91fd053393e321f5345723b3382722) since Edge Canary 148.0.3964.0. Its meaning is unknown. Our 12-node tree matches the shell of an awake Teams 26276 tree, so this flag alone does not explain the missing web content.
- **Documented.** Microsoft supports VoiceOver in Teams on Mac ([Use a screen reader to join a meeting in Microsoft Teams](https://support.microsoft.com/office/use-a-screen-reader-to-join-a-meeting-in-microsoft-teams-7f176bc8-68a8-4984-b9b3-ae907a8eaa69)).
- **Reported.** A [Microsoft Tech Community thread](https://techcommunity.microsoft.com/discussions/teamsdeveloper/enable-accessibility-tree-on-macos-in-the-new-teams-work-or-school/4033014) has no technical answer from Microsoft. One user says the tree works only while Accessibility Inspector is open. Another user says the tree had to be turned on for a subprocess, not the main app.

## Open points

- **Reported.** The delay differs. ai-translator saw the tree 0.069 s after the write. meeting-capture and EnviousWispr saw minutes. EnviousWispr woke it once by making Teams the active app.
- **Source.** Chromium waits 2 s before it acts on the switch. It uses a delayed call on the main run loop.
- **Unconfirmed.** We did not find what delays the switch for minutes in Teams.
- **Reported.** Read-back differs. ai-translator and Overtype read true after the write. Tally for Teams reads false.
- **Unconfirmed.** We do not know what turned the tree on before 2026-11-04 on this Mac. These are the candidates:
  - VoiceOver. Chromium has a VoiceOver path, and Microsoft documents VoiceOver in Teams.
  - Accessibility Inspector. A forum user says this, but nobody confirmed it.
  - Any tool that writes `AXEnhancedUserInterface`, for example screenpipe on the focused app.
  - Raycast and 1Password. They are closed source, so we could not check them.
- **Source.** Window managers such as [Rectangle](https://github.com/rxhanson/Rectangle/blob/451ab711b5c669dd49e14212c23b60db884f7a00/Rectangle/General/AccessibilityElement.swift#L224-L230) turn `AXEnhancedUserInterface` off before they move a window, and then restore the old value. A restore does not turn the tree on for the first time.

## Consequence for Mysli

1. Under the rule "Mysli only reads the Teams Accessibility tree. Never write attributes", Mysli cannot turn on the Teams web tree. It gets names only when VoiceOver or another tool turned the tree on in the current Teams process. After each Teams restart or update, expect the 12-node shell. Treat that state as "tree off" and keep the `Them` fallback.
2. Do not add an `AXManualAccessibility` write. Teams does not support it, so it does nothing.
3. The only measured way to turn the tree on is one write: `AXEnhancedUserInterface = true` on the application element of the `MSTeams` pid. Do not write it on the WebView process or on a window. This write breaks the current rule, so only the user can decide to allow it. If the user allows it, the projects above suggest these limits:
   - Read the value first. Write only when it is false, and never take the switch over from VoiceOver.
   - Write once for each Teams pid, and only while a recording with Teams names runs.
   - Ignore the return code. Check for `AXWebArea` or DOM identifiers after the write, and expect a delay of up to minutes.
   - Decide whether to set it back to false. The projects differ. A false write does not remove the Teams tree (reported), and in Chromium a false write can turn off support that another client asked for (source).
   - Expect side effects. Some projects say that `AXEnhancedUserInterface` changes window behaviour in some apps. ai-translator measured no CPU or energy cost from the switch alone. The cost comes from the reads.
4. You can still try two things that do not write, in a real call. The outcome of each is unknown. (A third check, the WebView command line, is done: no flag blocks the tree.)
   - Read `AXRole` on the `MSTeams` application element, then walk the tree again. This is Chromium's own read trigger, but ai-translator saw no effect from reads.
   - Turn VoiceOver on for a few seconds, turn it off, and walk the tree again. This is a user action, not a write by Mysli.
5. None of the other ways replaces the tree. Graph gives names only after the meeting, needs tenant admin consent, and sends a request to Microsoft. A media bot needs Windows Server and admin consent. Screen text recognition needs Screen Recording of meeting pixels and breaks when the layout changes. The local device API gives no speaker.
